1. Executive Brief: What We Are Actually Building
This is a marks-optimized academic full-stack project, not a startup and not a production SaaS product. The project is intentionally designed to be small enough to build quickly with AI-assisted coding, yet substantial enough to demonstrate frontend engineering, backend APIs, authentication, relational database design, business logic, role-based access, deployment, testing, documentation, and viva readiness.
Core principle  Working > ambitious. A stable 8-feature application that survives a live demonstration is worth more than a 25-feature application that breaks under questioning.
One-line project definition:
A web application for shared households to manage chores and common expenses, track individual contributions, calculate balances, and identify contribution imbalances through a shared dashboard.
Academic positioning:
The software is a shared household management and contribution-tracking system.
The “conflict resolution” element is supported through transparent records and contribution visibility, not through a claimed psychological or AI diagnosis.
The project uses synthetic demonstration data. No survey, interview, web-scraping, Kaggle dataset, or external research dataset is required.
Advanced features such as AI insights, mobile apps, payment gateways, push notifications, and automated reminders are explicitly Future Scope, not MVP requirements.

2. Scope Control and Anti-Waste Rules
The project will fail if the team keeps adding features while the deployment deadline approaches. The following rules are binding for the build.
No feature is added unless it improves marks, demo clarity, or a required synopsis section.
No new library is introduced when an existing library or browser capability is sufficient.
No database redesign after the core schema is approved without a documented reason.
No refactor of working code merely because the AI suggests a “better architecture”.
No real money movement. Expenses are records and calculations only; they are not payments.
No external datasets. Seed synthetic records instead.
No AI/ML model in the MVP. “AI analytics” belongs in Future Scope.
No microservices. One Express API is enough.
No complicated caching, queues, WebSockets, or background workers unless a later blocker proves they are necessary.
Every completed feature must be committed to Git before starting the next major feature.
Every live deployment change must be tested locally first.
When a bug is found, fix the smallest root cause; do not ask the coding AI to rewrite the whole project.
Definition of “done” for a feature  The UI works, the API works, the database persists the result, invalid input is handled, the feature survives refresh, and the feature is committed to Git.

Conceptually:

5.2 Why expense_splits Exists
An expense can be shared by multiple users and a user can participate in many expenses. This is an M:N relationship. Relational databases normally resolve that relationship through a junction table. Each expense_splits row records one participant and that participant’s share.
5.3 Data Integrity Rules
Every task belongs to exactly one household.
Every expense belongs to exactly one household.
Every expense split references a valid expense and valid user.
A user cannot join the same household twice.
Expense amount must be positive.
Invite codes must be unique.
Deletion rules should prevent orphaned records or explicitly cascade where safe.

8. Core Business Logic
The system needs only a small amount of real business logic, but that logic must be correct because it will be used in the demo and is likely to be asked about during viva.
8.1 Expense Split
Total Expense = T
Number of Participants = N
Equal Share per Participant = T / N
Example: ₹2,400 electricity bill shared among 4 participants gives an equal share of ₹600 per participant. The system stores the individual allocations in expense_splits.
8.2 Net Balance
Net Balance = Amount Paid by User - Expected Contribution
Positive balance means the user has paid more than their expected share. Negative balance means the user owes money relative to the shared records. This is an accounting-style record, not a payment transfer.
8.3 Chore Contribution
Chore Contribution = Sum of Points for Completed Chores by User
Points are configurable demo values chosen to demonstrate the application. They are not presented as a scientific measure of human effort.
8.4 Dashboard Contribution View
The dashboard displays chore points and financial balances separately so users do not confuse “money contributed” with “household work completed”. This is both technically clearer and easier to defend in viva.
Naming decision  Prefer “Household Contribution Balance” or “Contribution Overview” over a claim of a scientifically validated “Fairness Score”.

14.1 Viva Concepts to Understand
Authentication = proving who the user is.
Authorization = deciding what that authenticated user is allowed to do.
Primary key = uniquely identifies a row.
Foreign key = references a row in another table.
1:N = one record can be related to many records.
M:N = many records on both sides; usually implemented through a junction table.
Environment variable = configuration/secret provided outside source code.
API = interface through which the frontend requests backend operations.
CRUD = create, read, update, delete.
HTTPS = encrypted network transport between browser and server.
